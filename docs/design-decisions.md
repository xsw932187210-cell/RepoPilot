# 项目设计与失败案例讲解

这份材料供讲解设计时核对事实；量化结果以[证据索引](evidence-index.md)链接的固定实验为准。
它不是更新后的简历，也没有增加个人任职、生产用户或业务收益主张。

## 一条可以讲清楚的主线

RepoPilot 尝试把 Python Issue 变成可审查的候选修改。难点在于生成内容不可靠，同时模型、
数据库、文件系统和 GitHub 各有失败窗口。项目把检索和生成放进显式流程，并由程序决定
允许写哪里、测试是否通过、花了多少次请求、人工批准的是哪份修改。

Planner、Coder、Reviewer 是三种模型角色；Researcher 和 Test Analyst 是确定性只读节点。
图内只有 apply_policy 写候选，避免几个角色同时改同一份文件。候选先写私有暂存，再以
完整内容和摘要形成代次，数据库只选择完整代次。代价是磁盘、摘要和保留产物的成本；
目前没有自动保留期，也没有管理员之外的强文件系统隔离。

测试、人工审批和发布绑定同一个候选。用户看到的测试通过后，系统不能悄悄换成另一次
生成再发布。审批决定与恢复意图一起保存；Redis 不可用时保留 pending，允许显式重投。
发布先保存固定意图，再按远端状态对账。这里仍有数据库与远端请求无法原子提交的窗口，
所以记录 unknown 和 receipt，没有宣称 exactly-once。

模型预算也采用保守记账：先预留，再发请求。失败、重试、响应丢失都消耗次数；不知道
是否已执行时不退还预算。次数上限可控，但服务端 usage 不完整时无法得出准确金额。
应用的人工审批恢复做过实际 Worker 重启验证，任意阶段的自动崩溃恢复仍未实现。

## 应主动讲的负结果

早期 20 题中 oneshot 修复 15/20，workflow 13/20，后者请求数约为前者 3.1 倍。
新增的 3 题三策略重复对照也全部未通过独立验收。因此当前结论是工作流的治理能力和
可追溯性已经落地，修复质量提升尚未证明。

本轮离线查看了 18 个单元：7 个通过可见门槛仍未通过独立检查，3 个测试收集异常，
4 个调用控制停止且无修改，2 个运行错误，另有各 1 个预算耗尽与写意图拒绝。
它说明“执行器返回 completed”“模型审查结束”“进入人工审批”都不能替代真实修复验收。
由于隐私协议没有保留原始输出和临时候选，具体代码根因仍不确定；后续应在开发集保留
安全、可核查的诊断，固定一个变量再做新的独立验证。

## 可供追问的设计取舍

| 设计问题 | 当前选择及代价 |
| --- | --- |
| 为何多个角色仍然只有一个写者 | 角色提供不同职责；集中写边界后可统一检查权限、内容版本和批次完整性。多写者隔离尚未做 |
| 为何 Docker 测试之外还要独立验收 | 可见测试可能不覆盖缺陷症状；独立验收衡量修复效果。二者用途和数据出口不同 |
| checkpoint 为什么不等于任务不会丢 | checkpoint 保存图状态；队列出队、外部请求、文件写入各有独立失败窗口，需要另外的交付和恢复协议 |
| auto 为什么没有成为默认 | 本次可观测路由均为 workflow，没有覆盖轻路径收益，质量也未改善；保留显式选择和路由证据 |
| 为什么安装与镜像也属于交付 | 测试结论依赖具体依赖和运行环境；锁、镜像身份和独立资源让别人可以核查并重建验证条件 |

下一阶段的选择应由目标决定：CH-04 增强运行可靠性，CH-11/08A 增强工具边界，新的质量
方案验证修复效果。多人权限、管理界面和更多角色都还需要明确使用需求。
