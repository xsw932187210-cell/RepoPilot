### 已知现象与尚待验证的假设

| 方向 | 已确认 | 尚不能确认 | 下一次如何验证 |
| --- | --- | --- | --- |
| 检索 | 独立诊断在同一 20 例中覆盖全部预期修复文件；上述失败案例的首个相关文件排名为 1～3 | 命中文件是否包含了充分上下文、是否有噪声，以及模型如何使用上下文 | 新任务保留受控上下文身份与排名证据；按 CH-15 做组件消融，不直接新增向量检索 |
| 修改错误 | 9 项候选未满足全部独立行为，含两项 FTP 1/3 的部分修复 | 理解错误、编辑错误和上下文不足各占多少 | 在私有产物边界内审查候选，建立最小行为夹具；隐藏验收不回流给在线 Agent |
| 审查退化 | thefuck-002 有 2 轮修改及最终 high 风险否决；11 个修复成功的 workflow 仍有最终 Reviewer 否决，均为 low 风险 | 第一次候选是否正确、Reviewer 是否导致修改退化；low 风险意见是否属于误报 | CH-13 记录结构化审查依据和候选前后关系，在新实验中比较 Reviewer 开关/策略 |
| 权限拒绝 | 2 个任务被安全边界拒绝；边界发挥了阻止越权的作用 | 模型为何要求受保护文件、拒绝前的全部执行轨迹 | 先完成 CH-02B 的真实服务纠正与恢复验收；不放宽测试保护来提高通过率 |
| 环境/验收故障 | thefuck-002 未产生有效报告，原有测试身份也缺失 | 是候选破坏执行、环境异常还是其他原因；目前没有证据把它归为基础设施故障 | 保留受控的候选/执行证据，在隔离环境复现；缺少原始产物时保持未知 |

4 个 workflow 通过了流程内门槛，但独立验收未满足目标行为。这说明可见测试通过与最终修复成功是两个不同结果，现有隐藏验收仍有必要。11 个“成功但 Reviewer 否决”的观测说明模型意见与最终结果并不等价，不能直接据此宣布 11 次误报，也不能反推返工导致失败。

## 最小离线回归与重建

[计数夹具](../tests/fixtures/failure-observations-2026-09-09.json) 从上述原始来源抽取 6 条代表记录，覆盖验收报告缺失且伴有回归、流程测试通过但独立验收失败、安全拒绝、成对结果不同。全部测试标识转为计数，没有保留模型文本或候选代码。

[离线诊断测试](../tests/test_failure_analysis.py) 保护这些外部结果：

- 同一失败只计一个主分类，回归等辅助事实仍可查询；不根据轮数或 Reviewer 风险等级推定根因。
- 运行失败、配额等待、执行中、验收失败分别统计；未完成的配对不被算成某种策略获胜。
- 重复 case-mode 和混合实验指纹被拒绝，避免虚增分母或混用实验。
- 私有文本、隐藏测试标识、未知错误类型原文不会进入导出。
- CLI 记录源文件 SHA-256，并拒绝覆盖原始输入；公开账本仍可回算 40/38/28/12 的分母。

这些夹具复现诊断与计数行为，不重放历史模型补丁，也不替代 CH-02B 的 PostgreSQL/Worker 集成验收。

在已经安装项目的 Python 环境中，可从本机保留的原始文件重建：

```bash
python -m repopilot.failure_analysis \
  reports/real-v7-31-flash-lite/model-report.json \
  --output /tmp/repopilot-failure-ledger.json
cmp docs/evidence/2026-09-09-failure-ledger.json /tmp/repopilot-failure-ledger.json
pytest tests/test_failure_analysis.py -q
```

另一台机器若没有被忽略的原始 `reports/`，仍能运行公开计数夹具与测试，但不能据此重新获得历史原始执行记录。原始文件不同会改变 `source_sha256`，不能把重新生成的不同来源说成同一份逐字节证据。
